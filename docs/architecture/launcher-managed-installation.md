# Managed Launcher Installation

`OpenConquer.Launcher` and `OpenConquer.Client` are independently published components of one
installed OpenConquer product.

This document defines only that installed-product boundary.

## Schema-v1 Layout

```text
<product root>/
├── launcher files
├── openconquer.installation.json
└── client/
    └── client publish
```

`openconquer.installation.json` is generated by product composition:

```json
{
    "schemaVersion": 1,
    "productId": "OpenConquer",
    "clientRoot": "client"
}
```

Schema version 1 fixes `clientRoot` to exactly `client`.

It is not an arbitrary relative-path mechanism. A future topology change requires an explicit schema
evolution.

The descriptor defines layout only. It is not:

- a release manifest;
- an integrity or signature authority;
- an update source;
- authentication state;
- launch authorization.

## Ownership

The raw launcher publish does not contain:

```text
openconquer.installation.json
client/
```

Those are owned by product composition.

The launcher is a consumer of the installed layout, not its producer.

`OpenConquer.Product.Tool` is the repository's deterministic local/CI composition helper. It is not
a production installer or updater.

## Launcher Resolution

At startup, `ManagedInstallationResolver` begins at `AppContext.BaseDirectory`.

It requires:

- a valid schema-v1 descriptor beside the launcher;
- `productId` equal to `OpenConquer`;
- `clientRoot` equal to `client`;
- a real direct `client/` directory;
- no linked/reparse descriptor or client component.

It does not:

- ask the player to choose an installation directory;
- search the machine;
- inspect .NET runtime metadata to infer an installation;
- interpret arbitrary schema-v1 paths;
- follow linked client components.

Expected installation failures are represented explicitly rather than converted into a manual folder
selection flow.

## Launcher Lifecycle

`LauncherApplication` owns installation evaluation and launcher lifecycle state.

The relevant state flow is:

```text
Starting
    │
    ▼
EvaluatingInstallation
    ├── InstallationResolved
    ├── InstallationUnavailable
    └── Faulted

Stopping
    │
    ▼
Stopped
```

Shutdown owns state once it begins.

A resolver completion or failure racing with shutdown cannot overwrite `Stopping` with a later
installation or fault state.

`InstallationResolved` means only that the managed product boundary is present. It does not prove
release integrity or authorize the game to start.

## Product Composition

`OpenConquer.Product.Tool`:

- accepts independent launcher and client publish roots;
- rejects overlapping staging roots;
- rejects linked roots and linked entries;
- rejects launcher publishes that already own the descriptor or `client/`;
- stages through a temporary sibling directory;
- places the client publish under `client/`;
- rejects an empty client component;
- generates the schema-v1 descriptor;
- preserves Unix executable modes where supported;
- activates by directory rename without replacing an existing output.

Cleanup after failed staging is best-effort. Cleanup failure must not replace the primary staging
failure.

## Verification

The contract is protected at three levels:

1. Product Tool tests verify staging and descriptor generation.
2. Launcher tests verify descriptor validation and lifecycle behavior.
3. A cross-boundary integration test stages a real managed product with `OpenConquer.Product.Tool`
   and verifies that the real `ManagedInstallationResolver` accepts it.

CI additionally verifies that the raw launcher publish does not contain installed-product layout and
that the composed product does.
